  /** Call once per loop. Returns the volts for this side. */

  public double calculate(double measured, double goal) {

    // The volts we can predict: kS, kV and kA.

1   double ffVolts =

1       feedforward.calculateWithVelocities(lastGoal, goal);

    // The volts we couldn't: P works on what is left over.

2   double pidVolts = pid.calculate(measured, goal);

3   lastGoal = goal;

4   return MathUtil.clamp(

4       ffVolts + pidVolts, -MAX_VOLTS, MAX_VOLTS);

  }

1

Feedforward

Two goals in a row give it the speed and the acceleration.

2

P

Works on what is left. KP is 6 volts per m/s of error.

3

Remember the goal

This is why each side gets its own object.

4

Add, then clamp

Volts add together, and a motor only gets 12.

(1.5 min) First, the hardware. A speed loop needs a sensor, and FIRST’s KitBot code reads no encoders, so you add one per side. Our example uses a REV Through Bore Encoder on each wheel shaft, wired to the roboRIO, so this loop runs in Java every 20 ms. The stick now asks for meters per second instead of a share of the battery. VelocityDriveSubsystem makes one SpeedLoop per side, feeds it each encoder’s rate, and sends the volts with setVoltage. With kS in the loop, the dead spot is gone: in the simulator, a 0.3 stick creeps along at 0.05 m/s. The sysid section is ready to copy for your own robot.
