Common mistake

A vision pose stamped with the time now

What you see

Vision corrections look right while the robot is still. While it drives, they pull the estimate backward.

Why it happens

Timer.getFPGATimestamp() was passed in place of the frame’s timestamp, so the gap is measured at the wrong moment.

The fix

Pass est.timestampSeconds from PhotonLib, or mt2.timestampSeconds from LimelightHelpers.

WPILib docs: Pose Estimators

19

The frame shows where the robot was when it was taken. Stamped with the time now, the estimator compares it with where the robot is now. When the robot is still, those are the same place. When it drives, the vision pose looks behind, so each correction pulls the estimate back. Both libraries give a timestamp on the robot’s FPGA clock, which is what WPILib’s estimator expects. PhotonLib syncs the clocks for you. LimelightHelpers subtracts the Limelight’s reported latency from the time the data arrived.
